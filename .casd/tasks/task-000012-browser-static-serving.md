# Browser-test static serving

Goal: [goal-000002](../goals/goal-000002-staged-dependency-upgrades.md)

## Objective and authorization

Repair the browser-test static-serving defect and its false-green verification gap before staging or further dependency upgrades. The human explicitly requested this repair after seeing repeated unhandled TypeError tracebacks in otherwise successful checks. A successful browser scenario must not conceal unexpected application/static request failures. This is test infrastructure repair, not a production static-serving change or a dependency upgrade.

## Established cause, contracts and owners

- On accepted revision `1f52fb128aa7253b004cc9f9059c3e07232452ec`, a focused run of `schedules.tests.test_float_schedule_inputs.FloatScheduleInputBrowserTests` reproduced five `TypeError: expected str, bytes or os.PathLike object, not NoneType` tracebacks while reporting `OK` (one test). The Float runner loads real page assets but checks the main document and form semantics, not failed asset requests.
- `preceptor_project/test_settings.py` inherits `settings.py`, leaving `STATIC_ROOT=None`. Ordinary Django `LiveServerTestCase` uses `_StaticFilesHandler`, which passes that value to filesystem serving. Multiple browser classes declare `serve_static=False`; Django does not consume that attribute. A direct request for `/static/schedules/application.css` through this handler reproduces the exception without a database.
- Django owns live-server/staticfiles handling. Its supported `django.contrib.staticfiles.testing.StaticLiveServerTestCase` serves through staticfiles finders without collectstatic: https://docs.djangoproject.com/en/5.2/howto/static-files/#testing and https://github.com/django/django/blob/5.2.17/django/contrib/staticfiles/testing.py . Prefer this conventional abstraction rather than a custom file server, fabricated production STATIC_ROOT, or monkeypatch of Django internals.
- Inspect every current `LiveServerTestCase` consumer, including `schedules/tests/*browser.py`, `test_float_schedule_inputs.py`, and `test_schedule_reports.py`. Existing runners often fulfill selected local assets or intentionally abort excluded resource requests. Preserve legitimate scenario isolation and no-JavaScript assertions; it is not necessary to turn every layout test into a full asset integration test.
- `schedules/tests/browser_tools.py` owns pinned tooling discovery; `browser_session.cjs` owns existing Playwright lifecycle/deadline/cleanup; `test_browser_session.py` protects primary error preservation and owned profile cleanup. Several older runners manage browser teardown directly. `scripts/check` runs the supported offline browser tooling, JavaScript tests and parallel Django suite; `scripts/quality-check` owns fast non-mutating verification. Reuse these owners and standard Playwright request/response events, not a second browser framework or a log-grep success oracle.
- `README.md`, deterministic project check/browser tooling paragraphs, defines fail-closed tooling, offline checks, and teardown. `docs/design.md` section 26.3 preserves the pinned Ruff/shared-virtualenv convention; section 27 calls for cohesive explicit owners rather than generic frameworks. Sections 26 and the commissioned deployment direction retain separate production/staging static roots and deployment topology. `docs/staging.md` remains a remote-operation boundary, not a browser-test configuration source.

## Acceptance

1. Existing browser-test live servers serve actual application CSS and JavaScript through supported Django staticfiles behavior without a configured collected STATIC_ROOT or the reported TypeError. Trace the same faulty assumption across all current browser-test consumers and remove ineffective configuration. Preserve current production/development/staging configuration, pins, models, application routes, semantics and browser assertions.
2. Real HTTP/browser evidence covers an existing stylesheet and script with successful status, appropriate content type and identifiable content, and a nonexistent static asset with ordinary 404 rather than 500/traceback. Include at least one affected scenario using actual asset transport (the Float browser scenario is the known reproduction); mocked route fulfillment alone cannot establish the repair.
3. Unexpected application/static request failures in the affected browser runners become test failures with the request URL and useful status/error diagnosis, including auxiliary requests that currently escape document-only assertions. Cover HTTP server errors and failed/missing required assets, not just JavaScript page exceptions. Keep this narrow and reusable at the existing browser-test boundary. Do not silently swallow errors, redirect stderr, disable asset requests globally, remove assertions, skip browser coverage, or rely solely on a clean log check. Intentionally fulfilled/aborted test routes and explicitly tested error responses may remain, but exceptions must be tied to the intentional scenario/request rather than allowing all failures of an error class. Preserve existing deliberately no-JavaScript/layout scenarios without pretending they verify runtime asset delivery.
4. Demonstrate that representative unexpected failed asset/server responses make the Node runner and enclosing Django test fail even when page-content assertions could otherwise succeed; the correct configuration passes. Negative evidence may use existing test seams or retained fault-injection evidence rather than permanent broad test infrastructure. Detection must await relevant request outcomes before declaring success, without sleeps, race-sensitive quiet-period assumptions, or unbounded waits. Expected teardown cancellation must not replace the original scenario error. Preserve Playwright-owned cleanup/deadlines and existing test resource ownership.
5. The focused failing-before case passes without the reported traceback afterward, relevant browser tests pass, and both `scripts/quality-check` and complete `scripts/check` pass with browser coverage and existing exclusions unchanged. Inspect output, not just exit codes: remaining unexplained unexpected tracebacks/errors are unresolved verification failures and must be reported. Intentional negative tests must keep attributable expected diagnostics separate from unexplained application failures. Briefly document the static-serving and failure-detection convention in the existing developer-check documentation.

## Scope and evidence

Use the shared main-repository `.venv/bin/python` and existing declared Chromium/Node installation. No dependency upgrades, production/staging access or deployment, pushes, data resets, network-dependent Checks, new global test matrix, or redesign of browser process lifetime. Temporary fixtures use Django test databases and invocation-owned resources only; remove exact owned scratch resources on success/failure and report residue. Cassidy owns its worktrees.

Record tested revision, before/after reproduction, affected consumers, failure-detection negative evidence, focused and full results, unexpected-output assessment and cleanup. Exact Candidate Check and independent Review remain mandatory; the coordinator owns acceptance, exact-revision GitHub output verification and any later staging handoff. This repair must not claim that already-green historical checks were clean or that production static serving was proven broken.

## Execution strategy

Begin with the focused Float browser case and identify the failed resource URLs using ordinary Playwright observations, retaining failure evidence. Apply the standard Django staticfiles test-server boundary consistently where the same assumption exists. Then wire the smallest shared request-failure assertion through current browser runners, preserving intentional interception and existing lifetime owners rather than migrating all lifecycle code for convenience. Prove the guard against a deliberately failing required request as well as the repaired real asset path; a positive-only smoke test would miss the false-green mechanism. Run the existing browser evidence and full Check last and inspect their captured output. Equivalent supported mechanisms meeting these obligations are acceptable; no particular helper-call sequence or raw SQL/HTML/output snapshot is required.
