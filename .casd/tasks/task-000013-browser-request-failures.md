The human authorized fixing the false-green browser verification after repeated live-server TypeErrors in successful checks. Run after accepted task-000012, which repairs Django static transport and proves real CSS/JavaScript delivery and missing-asset 404 behavior. Preserve those independently useful guarantees and tests; this Task adds failure observation, not another transport repair. ## Acceptance

1. Unexpected application/static request failures in current browser runners produce a nonzero runner result and a failed enclosing Django test with useful URL/status or transport-error diagnostics, even if the main document and page-content assertions pass. Cover HTTP server errors and failed/missing required assets, not merely page exceptions. Integrate at the existing browser-test boundary using a small shared mechanism where useful; trace all relevant current runners rather than repairing only Float.
2. Intentional route fulfillment/aborts, tested error responses and deliberately no-JavaScript scenarios retain their meaning. Any expected-failure exception is explicit and scoped to the intentional scenario/request, not a broad status/error-class exemption. Existing required asset errors must not disappear by moving them into ignored requests. This is not a mandate to turn isolated layout tests into full production asset integration tests. Keep the predecessor's actual asset transport evidence intact.
3. Failure observation completes before success is reported, including relevant auxiliary request outcomes. Use supported events and explicit bounded completion points, not sleeps, arbitrary quiet-period guesses, global network-idle assumptions or unbounded waits. Distinguish deliberate teardown cancellation from scenario failures; preserve primary errors and existing Playwright cleanup/deadline responsibilities. Do not inflate unrelated timeouts or introduce a watchdog that kills only Node and abandons Chromium.
4. Negative evidence proves a representative failed required asset and a server error cause runner/enclosing-test failure despite otherwise successful content assertions. Also verify that intentional fixture routing remains accepted and that errors retain actionable request attribution. Use feasible local test fixtures and existing runner seams; avoid a broad lifecycle cross-product or duplicating assertions across every runner. Fault injection may be retained Attempt evidence when a permanent test would freeze temporary wiring. Assertions must permit equivalent helper organization and harmless presentation changes.
5. Focused browser tests, existing cleanup tests, `scripts/quality-check` and complete `scripts/check` pass with browser coverage/exclusions unchanged. Inspect output, not just exit codes: unexplained unexpected tracebacks remain unresolved. Expected negative-test failures must be captured and asserted rather than silently ignored. No stderr suppression, skipped tests, weakened assertions or log-grep-only success oracle. Document the request-failure convention and intentionally scoped exceptions in the existing developer-check documentation.

## Execution strategy

Inspect current interception and explicit error scenarios before choosing a shared observer API; this prevents an overly broad exception rule or breaking no-JavaScript fixtures. Install observations before navigation, integrate failure assertions at the current runners' completion boundaries, and verify failure propagation through Node into Django. Prove a controlled failed asset/server response is caught before broad reruns. Retain existing lifetime owners and direct transport regressions instead of coupling detection to a new server or migrating unrelated lifecycle code. Finish with browser/cleanup regressions and full checks, inspecting captured output for unexplained failures.
