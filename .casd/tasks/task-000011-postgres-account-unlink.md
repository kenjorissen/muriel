# PostgreSQL account unlink repair

Goal: [goal-000002](../goals/goal-000002-staged-dependency-upgrades.md)

## Objective and accepted direction

Restore Physician/account unlinking on PostgreSQL without changing its authorization, retained-history or transaction semantics. The human approved fetching and locking the Physician without a nullable join, separately fetching and locking its linked account within the same transaction when present, then clearing the link and recording history; an already-unlinked Physician remains a no-op. Deliver this repair before retrying the separate Psycopg upgrade. This is an independently useful persistence repair, not a dependency-version change.

## Acceptance

1. Under actual PostgreSQL 18, an authorized unlink of a linked Physician succeeds without nullable-join locking, clears only that relationship, preserves both records and all unrelated facts, and records the accurate prior account identity, null resulting identity, actor/time and optional reason. Unlinking an already-unlinked Physician succeeds without another change record. No schema or dependency-pin change.
2. Preserve the existing scheduling-administrator guard, shared mutation authority and atomic operation. Lock the Physician and, when present, its linked account through separate ordinary Django ORM queries in the same transaction. Do not replace locks with an unlocked read, weaken them to self-only locking of a joined result, exclude unlinked Physicians, or invent a generic locking abstraction. History failure or outer transaction rollback must restore the link and leave no partial history. Do not broaden this into a new application-wide lock-order policy; surface any consequential problem outside the repair boundary.
3. The shared callers continue to replace/remove account links with their existing account and Physician histories and permission checks. Account-link-only changes still leave retained Precepting month edit times unchanged. Trace similar lock/join assumptions proportionately; unrelated nonnullable joins are not cleanup targets.
4. Actual separate-connection PostgreSQL evidence establishes that both existing rows remain protected during the enclosing transaction and their locks release after completion, including rollback. Avoid timing guesses and sleeps: use Django's normal transaction facilities and deterministic NOWAIT or controlled synchronization. SQLite behavioral evidence remains required but cannot prove this row-lock obligation.
5. Focused behavioral tests pass on PostgreSQL and SQLite, and the existing `scripts/quality-check` and `scripts/check` pass without changed exclusions, missing browser coverage or weakened assertions. Extend existing owning tests only for uncovered no-op/authorization/rollback/locking obligations. Equivalent query organization that preserves the approved separate-lock behavior must not be rejected by brittle SQL-string or helper-call assertions.
