# Django 5.2.19 security patch

Goal: [goal-000002](../goals/goal-000002-staged-dependency-upgrades.md)

## Objective and boundary

Upgrade Django 5.2.17 to 5.2.19 as a useful security-patched baseline before the separately reviewed 6.1.3 transition. This delivers upstream fixes without requiring the larger framework migration to succeed. The subsequent upgrade retains these security guarantees and application behavior; the exact intermediate pin is one-time delivery evidence, not a permanent test assertion.

Run after accepted task-000010 (Gunicorn 27.0.0). The coordinator owns the preceding server staging gate. Only this Django pin and necessary directly attributable compatibility repairs/documentation are in scope. Preserve all other direct dependency pins, Python 3.14, PostgreSQL 18, SQLite development, security defaults and application semantics. No schema redesign, feature adoption, new mail infrastructure, or framework replacement.

## Owners and contracts

- `requirements.txt`; Django's ORM, forms, authentication, request parsing and email implementation remain the conventional owners. Preserve `preceptor_project/{settings,production_settings,staging_settings,test_settings}.py` deployment identities and test isolation.
- `docs/design.md`: accepted month-calendar edit recorder (atomic edits/history/timestamps and rollback), section 4 SchedulingMutationAuthority, section 7.2 history/time, section 15.2 retained human-reviewed proposal Apply, section 26 conventional Python/Django/database runtime.
- `docs/password-recovery.md`: indistinguishable recovery response, synchronous invitation failure handling and no live mail from tests. `docs/public-edge.md`: HTTPS, authentication and private Admin boundaries. `docs/staging.md`: isolated database identity and non-reset updates. `docs/deployment.md`: exact-release deployment and no automatic database rollback.
- Read the official 5.2.18 and 5.2.19 release notes at `https://docs.djangoproject.com/en/5.2/releases/5.2.18/` and `/5.2.19/`. They include header-parsing, multipart-memory, cache-key, formset and GeoDjango fixes. This application does not thereby gain GIS or a new cache layer. Security-fix presence is distinct from demonstrated application exploitability or an exhaustive audit.

## Acceptance and verification

1. Install and declare Django 5.2.19 in the shared main virtualenv; record Python/Django and relevant backend versions. Assess required transitive resolution and report changes rather than silently broadening direct pins.
2. Existing valid requests, uploads/imports, forms, authenticated scheduling, invitations and password recovery retain their behavior. Do not revert stricter handling of malformed input merely to restore legacy acceptance. Reuse the owning tests in `test_password_lifecycle.py`, `test_scheduler_invitations.py`, `test_public_authentication.py`, `test_public_edge.py`, and workbook/import owners; inspect and resolve unexpected traceback output instead of accepting a green exit alone.
3. SQLite `./scripts/quality-check` and `./scripts/check` pass, including browser static transport and request-failure enforcement. No test skips, broad warning suppression, disabled observers, weakened authorization or mutation assertions to accommodate the patch.
4. A fresh disposable PostgreSQL 18 database can apply the entire existing migration chain. Run the same focused mutation, month-edit, account unlink and retained-proposal behavior on PostgreSQL as SQLite; preserve accepted row locks, rollback, identity and history. No application migration is expected; investigate and justify any genuine framework-required change rather than blindly regenerate migrations.
5. Run `./scripts/security-audit` and retain actual output, including any unrelated finding or service failure. An audit failure must be classified, not waived or presented as clean. Exact Candidate Check and independent Review are required before coordinator acceptance.

## Resource and execution boundary

Use the shared main-repository Python interpreter and normal Django test runner. An invocation-owned `postgres:18-alpine` container and temporary test settings are permitted for compatibility evidence, not new deployment architecture. Restrict exposed transport to loopback and use only generated test credentials/data. Record exact resources; the worker stops/removes its own container, volumes, scratch settings and any test processes on success/failure, retaining results in Attempt evidence. Do not touch other containers, application databases, protected configuration or mail services. No pushes, PR disposition, deployment, live staging/production access, resets, sudo or credentials changes. The coordinator owns exact-revision GitHub checks and staged verification.

## Execution strategy

Read the narrow upstream fixes and owning tests before installing only the patch. Exercise request/authentication/import regressions and fresh PostgreSQL migrations first to isolate patch compatibility, then normal full checks and audit. Existing behavioral assertions are the evidence baseline; add a test only for an uncovered consequential application contract or a necessary compatibility repair. Do not reproduce Django's entire security test suite locally.
