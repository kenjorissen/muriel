# Django 6.1.3 compatibility upgrade

Goal: [goal-000002](../goals/goal-000002-staged-dependency-upgrades.md)

## Objective and predecessors

Move the application from the accepted security-patched Django 5.2.19 baseline (task-000015) to Django 6.1.3, preserving its existing product, persistence and deployment contracts. Require accepted Gunicorn 27.0.0 and the coordinator's server staging gate first. This is one framework-compatibility outcome, not permission to introduce the framework's new features or redesign independent application behavior. If an independent defect/repair is needed beyond compatibility, report it for separate planning rather than absorb it silently.

## Contracts and owning integration

- `docs/design.md`: accepted month-calendar Precepting and its edit-time recorder; section 4 SchedulingMutationAuthority; section 7.2 retained history/time; section 15.2 human-reviewed solver Apply; section 26 conventional synchronous Django, Python 3.14, PostgreSQL production and SQLite development. Preserve organization-local dates, atomic edits/history/timestamps, nested rollback, stale proposal refusal and both-row account-unlink locking.
- `docs/password-recovery.md`: recovery confidentiality, manual versus synchronous SMTP invitations, stable `PRECEPTOR_EMAIL_*` environment contract, bounded transport settings and failed-delivery persistence. `docs/public-edge.md` and `docs/production.md`: proxy/host/CSRF/cookie policy, Unix-only production trust and private Admin. `docs/staging.md`: isolated loopback HTTPS trust and separate database. `docs/deployment.md`: fresh/existing migration and exact-release readiness; no automatic rollback after migrations.
- Owners: `requirements.txt`, Django's ORM/migration/form/authentication/email/staticfiles layers; project settings and middleware; `schedules/services/{_mutation,month_edits,accounts,slot_projection,precepting_solver}.py`; models and the existing migration chain. Prefer supported Django APIs, never a replacement query/parser/auth stack or patches to installed Django.
- Read official release notes for 6.0 and 6.1 plus patches through 6.1.3 (`https://docs.djangoproject.com/en/6.1/releases/`). Relevant changes include removed deprecated constraint/model/form APIs, combined-queryset ordering, cleared-ordering `first/last`, all-database default checks, SQLite >=3.37, email API changes and stricter multipart parsing. `slot_projection.py` combines explicitly unordered Normal/Casual Rounding value queries; establish behavior on both databases rather than assuming SQL compatibility. Settings already explicitly select BigAutoField. The application uses Django's `EmailMultiAlternatives` and built-in recovery, not a custom message engine.

## Acceptance

1. Pin/install Django 6.1.3 using the shared main virtualenv. Record resolved Python, Django, SQLite and PostgreSQL/Psycopg versions and required transitive changes. Preserve other direct pins. Python remains 3.14 and PostgreSQL 18; do not downgrade supported platforms or adopt async/ASGI, background tasks, pooling or database-native cascading as part of compatibility.
2. Fresh SQLite and PostgreSQL 18 databases apply the entire migration chain, and a disposable database migrated/populated under the accepted 5.2.19 baseline remains usable under 6.1.3 with its records and relationships intact. Use synthetic data, never live databases. Check migration drift; no schema change is expected merely because a default changed. Do not rewrite historical migrations without a demonstrated necessity, or invent compensating schema changes for obsolete test expectations.
3. The same owning behavioral tests on SQLite and PostgreSQL preserve mutation locking/rollback, month-edit recording, retained solver Apply/staleness/history, account identity/unlink and the combined Rounding projection. Reuse `test_scheduling_mutation.py`, `test_month_edits.py`, `test_precepting_solver.py`, `test_physician_account_identity.py`, and the relevant slot/master-schedule tests. Include actual independent-connection lock exclusion/release, not only the process-local lock.
4. Existing sign-in/out, reset/change and invitation flows, permissions, CSRF, public/private Admin boundaries, imports/uploads, PDF exports and browser behavior pass. Keep the accepted browser static-server fix and terminal/redirect request-failure detector effective. Validate static collection/manifest serving and valid synchronous HTTP through the existing Gunicorn runtime probes; do not change transport or trust topology.
5. Keep the existing operational email inputs and default manual/console/test-locmem modes. Where supported deprecated APIs still work, record their deprecation and a bounded follow-up rather than adopting a new product outcome under this Task. If a compatibility change is required, trace settings, invitation/recovery consumers, tests and docs together; no live mail or outbound-service dependency. Do not conceal new warnings with broad filters.
6. `./scripts/quality-check`, `./scripts/check`, and `./scripts/security-audit` pass with inspected output. Necessary fixture/API adaptations preserve the same requirements, not current private representations. No ignored/skipped tests, removed security checks, schema drift exemptions or reduced backend promises to make the major upgrade pass. Exact Candidate Check and independent Review must evaluate the resulting complete change.

## Resource and execution boundary

Use only normal project runners and the shared interpreter. Test-owned PostgreSQL 18 containers, loopback listeners, Unix sockets, scratch settings, databases and generated PDF/static artifacts are permitted. Record exact ownership; the worker terminates/removes its own processes, containers/volumes and scratch on success/failure and retains result evidence. Never mount real databases or protected host configuration, touch unrelated processes/containers, send real email, or obtain credentials/sudo. No pushes, remote changes, deployment, reset, live staging/production access or production rollout. The coordinator owns GitHub and non-reset staging verification and must not infer authenticated smoke from public readiness.

## Execution strategy

Map the removed/changed Django APIs to actual consumers first. Before replacing the shared installation, create a synthetic 5.2.19-migrated database for upgrade evidence; then install 6.1.3, test its fresh and existing migration paths and key cross-backend mutations. Exercise auth/email/static/server integration using established fixtures before broad checks. A supported conventional adaptation is preferable to compatibility wrappers. Classify each failure as application defect, framework compatibility or fixture overspecification before editing expectations; stop on a material contract conflict.
