# Gunicorn proxy trust repair

Goal: [goal-000002](../goals/goal-000002-staged-dependency-upgrades.md)

## Objective and accepted direction

Align Gunicorn's production forwarding-header trust with Muriel's existing Unix-only proxy contract, while preserving staging's separate loopback HTTPS forwarding. The human explicitly approved disabling TCP forwarding-header trust for production, preserving staging's intended trust, and continuing upgrades. Deliver this independently useful security/configuration repair at the accepted Gunicorn 23.0.0 pin before task-000010 upgrades the server. No dependency-pin or live-service change belongs to this Task.

## Evidence, contracts and owners

- Blocked Attempt `2863050-1794493336954363734-0` on `b258bff578fcbb0d06ce3cb236526415ceca1b38` produced no Candidate. Its real Gunicorn 26.2.0 loopback probe passed `X-Forwarded-Proto: https` to production middleware. Gunicorn had already set `wsgi.url_scheme=https`; stripping the header did not restore the expected HTTPS redirect. Admin-marker rejection worked. Production's commissioned listener is Unix-only; this was a disposable network-peer conformance test, not a demonstrated public production bypass.
- `scripts/start-production` is the shared production/staging launcher. `preceptor_project/production_proxy.py` strips forwarded protocol and private-Admin markers from non-Unix peers. `production_settings.py` selects that middleware, HTTPS redirect and secure-cookie policy. `staging_settings.py` intentionally trusts its loopback Tailscale Serve hop. Gunicorn owns parsing headers into the WSGI scheme before Django executes; do not patch around that ownership by blindly rewriting `wsgi.url_scheme` in middleware.
- Official Gunicorn `forwarded_allow_ips` documentation: https://docs.gunicorn.org/en/23.0.0/settings.html#forwarded-allow-ips . Its default trusts loopback; an explicit empty IP allowlist removes TCP peers, while Unix connections remain trusted independently. This conventional configuration path is the approved repair; do not add a custom proxy-header parser, new environment-controlled trust policy or alternate listener.
- `docs/design.md` section 26 commissioned deployment direction, `docs/production.md` Service command, and `docs/public-edge.md` public/private proxy contracts retain Nginx-to-Gunicorn Unix transport, overwritten headers, private Admin marker and exact-host trust. `docs/staging.md` retains fixed loopback port 8082, private HTTPS port 10000 and staging-only identity. Update the narrow owning runbook text to record the accepted server-level production trust rule and staging distinction; no topology redesign.
- Owning evidence: `test_production_runtime.py::ProductionLauncherTests` uses a fake interpreter and verifies effective launch options; `test_production_settings.py::test_only_the_unix_socket_proxy_https_header_prevents_the_https_redirect` injects REMOTE_ADDR through Django's client; `test_public_edge.py::PrivateAdminTransportTests` protects network-marker rejection, trusted Admin login and secure sessions. These tests cannot by themselves prove Gunicorn's actual pre-Django scheme conversion. `test_staging_instance.py` protects staging settings and static/readiness behavior.

## Acceptance

1. The production launcher explicitly configures an empty Gunicorn forwarded IP allowlist using its supported setting, with argument quoting that preserves the empty value. Production retains Unix socket/umask, unprivileged foreground execution, worker/time bounds and logging. Inherited `FORWARDED_ALLOW_IPS` or ordinary Gunicorn environment arguments must not silently broaden the fixed production boundary; use documented configuration precedence and proportionate adversarial environment evidence, not a generic environment sanitizer.
2. Staging preserves its existing loopback HTTPS semantics and fixed bind. Production-only hardening must not disable staging's legitimate forwarded HTTPS or change its settings/data/identity. Keep Unix-proxy protocol and private-Admin headers usable; network-peer private-Admin spoofing remains rejected.
3. At actual Gunicorn 23.0.0, a disposable TCP request under production policy with spoofed forwarding headers is not treated as HTTPS and still receives the appropriate HTTPS redirect, while a trusted Unix request retains expected secure behavior. Trace all Gunicorn-supported scheme-header aliases rather than repairing only one header spelling. Actual separate staging-policy loopback evidence confirms legitimate HTTPS forwarding survives. Exercise Gunicorn and the owning Django middleware together: mocked argv or Django Client alone is insufficient. Restore only the shared environment's Gunicorn to accepted 23.0.0 first (the blocked upgrade left 26.2.0 installed), report the version, and reproduce the old-default failure before the repair where practical; do not assume a new-version regression.
4. Extend existing owner tests and add only the narrow real-server conformance evidence needed for this trust boundary. The server policy used in the real probe must be tied to the actual launcher behavior, not an independently handwritten desired value that could pass while the launcher is wrong. Preserve existing login, CSRF, secure-session and private-Admin assertions. Equivalent supported configuration syntax is allowed; test semantics, not incidental logs, PIDs or formatting.
5. `scripts/quality-check` and `scripts/check` pass without weakened exclusions or missing browser coverage. Inspect output for unexplained errors, not merely successful exit. No schema, dependency pin, application scheduling behavior, service identity, privileged path or runtime topology change. No control-socket flag requiring newer Gunicorn yet; task-000010 owns that upgrade-specific change.
